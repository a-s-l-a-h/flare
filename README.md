# Flare

**Server-Driven UI for Phoenix + DivKit.** Build native Android, and Web
apps from one Elixir codebase — your screens are Elixir modules, your UI is
JSON, and updates ship instantly .

This document is the complete developer reference for the Flare framework
itself (the `flare/` library). It explains the architecture, every public
API, the screen lifecycle, state management, caching, authentication, and
how to build a new project on top of it.

> ⚠️ **This is a proof of concept — version 0.5, not production ready.**
> It demonstrates the SDUI architecture and core ideas. APIs will change. Use it to understand the pattern, run the demo, and build on these concepts.

## What Flare Is

Flare is a Server-Driven UI (SDUI) library that sits on top of Phoenix
Channels. Instead of shipping a native UI in your app binary, your app ships
a *renderer* (DivKit, on Web/Android/iOS), and the actual screen layouts —
what buttons exist, what text they show, what happens when they're
tapped — are JSON documents generated by your Elixir server at runtime.

Concretely, a "screen" in Flare is:

- **One Elixir module** (a `Flare.Screen`) that owns the screen's server-side
  logic: what data to load on mount, what happens on a button tap, what
  state variables the screen exposes to the client.
- **One `layout/<screen>.json` file** — a DivKit card describing the UI tree
  (containers, text, images, buttons, inputs, etc.), with placeholders like
  `@{flare_count}` for values that come from the server.
- **One (optional) `state/<screen>.json` file** — declares the *type* and
  *default value* of every variable the layout references.

Every screen maps 1:1 to a Phoenix Channel topic: `"flare:<screen_name>"`.
When a client joins that topic, the server:

1. Authenticates the connection (host app's job, via `UserSocket`).
2. Authorizes access to that specific screen (`authorize/2` or router
   `roles:`).
3. Runs your screen's `mount/2` callback (query the DB, compute values).
4. Sends the client an `"init"` envelope containing the layout JSON, the
   variable type definitions, and the current values.
5. From then on, `handle_event/3` handles taps/inputs from the client, and
   any state changes are diffed and pushed to the client as tiny `"patch"`
   messages — never the whole layout again.

Flare is transport- and rendering-agnostic on the wire (JSON over
WebSocket, or a custom gzip binary frame for large payloads — see
[The Binary Protocol](#the-binary-protocol--optimize)), and the actual
widget rendering is handled entirely by DivKit on each platform. Flare's
job is: manage the channel, manage per-user state, diff it, and ship
patches.

**Flare never handles authentication or authorization of users at the
identity level.** It relies entirely on the host Phoenix application to
verify tokens in `UserSocket.connect/3` and hand Flare a `user_id` string.
This is by design — Flare doesn't want to be opinionated about how you log
people in.

## Getting a New Project Up and Running

Everything below assumes you already have the Flare monorepo layout locally
(the `flare/` framework, the two client SDK folders, and
`flare_app_template/`), and that you've generated a new project from it
using `create_flare_project.py` (see the [Project Generator
Script](#the-project-generator-script) section for exactly what the script
does and why the layout looks like this).

### Step 1 — Run the generator

```bash
python3 create_flare_project.py

```

You'll be prompted for:

-   **Project name** — this becomes your Elixir app name (snake_case) and module prefix (PascalCase). E.g. entering `Coffee Shop` produces app `coffee_shop` and modules under `CoffeeShop.*`.
-   **Destination folder** — where the new project directory tree should be created.

This produces:

```
<destination>/<project_name>/
├── flare/                     ← the framework, copied verbatim
├── flare-android-client/      ← Android SDK, copied verbatim
├── flare-web-client/          ← Web SDK, copied verbatim
├── .gitignore
├── README.md
└── <project_name>/            ← YOUR new Phoenix app (renamed from the template)

```

### Step 2 — Install Elixir & Erlang/OTP

If you don't already have them:

```bash
elixir -v

```

If that command isn't found, install from https://elixir-lang.org/install.html (Erlang/OTP 25+ and Elixir 1.15+ recommended — this matches what `flare_app_template/mix.exs` and `flare/mix.exs` declare as minimum versions).

### Step 3 — Build the web client

The web client is a small esbuild-bundled JS app (Phoenix JS client + DivKit + Lottie) that gets served as static assets by your Phoenix endpoint. It needs to be built once (and rebuilt whenever you change `flare-web-client/src/js/*` or want fresh `dist/` output):

```bash
cd flare-web-client
npm install
npm run build

```

Check `flare-web-client/package.json` for the exact build script name — by convention this project uses a `build` script that runs `scripts/copy-files.js` (copies `index.html`, `app.css`, and `static/` into `dist/`) alongside the JS bundler. The output lands in `flare-web-client/dist/`, which is exactly the path your generated app's `Endpoint` and `PageController` expect (see `page_controller.ex` and `endpoint.ex` — they resolve `../../../../flare-web-client/dist` relative to the app, i.e. as a sibling of your app folder — this only works because the project generator preserves that exact sibling-folder layout).

> **Do not move `flare-web-client/` relative to your app folder.** The relative path depth (`../../../../`) is baked into `lib/<app>/http/endpoint.ex` and `lib/<app>/http/controllers/page_controller.ex`. If you restructure the folders, update those two `Path.expand` calls to match.

### Step 4 — Fetch Elixir dependencies

```bash
cd <project_name>            # the inner Phoenix app folder
mix deps.get

```

This pulls Phoenix, Bandit (the HTTP server), Ecto/Ecto SQLite3, Joken (JWT), Pbkdf2 (password hashing), and — critically — `{:flare, path: "../flare"}`, which is a **path dependency** pointing at the sibling `flare/` folder. This is why the generator places `flare/` as a sibling of your app rather than inside `deps/` — Flare is designed to be vendored alongside your app, not pulled from Hex, so you can read/patch it locally if needed.

### Step 5 — Create and migrate the database

```bash
mix ecto.create
mix ecto.migrate

```

The template ships with a SQLite database (see `config/config.exs` — `adapter: Ecto.Adapters.SQLite3`) and starter migrations for `users` and `identities` (see [Authentication](https://claude.ai/chat/594413f3-2e86-417b-b7bd-00ffdf283354#authentication--tokens)). Add your own domain migrations under `priv/repo/migrations/` as you build out your app.

### Step 6 — Start the server

```bash
mix phx.server

```

By default this binds to `http://0.0.0.0:4000` (see `config/dev.exs`). Open `http://localhost:4000` in a browser — you should see the login/guest screen from `flare-web-client/src/index.html`, and after signing in (or continuing as guest) you'll land on your `home` screen.

For interactive debugging, you can also boot into an IEx shell attached to the running server:

```bash
iex -S mix phx.server

```

This is useful for calling `Flare.push_to_user/3`, `Flare.broadcast_to_screen/2`, etc. by hand while developing, or for running the included memory/traffic diagnostic (`YourApp.Utils.FlareMemoryAudit.run()` — see the file at `lib/<app>/utils/flare_memory_audit.ex` for full usage instructions in its moduledoc).

```
│       ├── http/
│       │   ├── endpoint.ex         # Phoenix.Endpoint — static assets + /socket
│       │   ├── http_router.ex      # Plain HTTP routes: /auth/*, catch-all → PageController

```

Note the pattern: **`lib/<app>/flare_app/`** is where 100% of your Server-Driven UI lives (screens, scaffold, router). **`lib/<app>/core/`** is where your plain Elixir/Ecto business logic lives, completely decoupled from Flare — screens call into `core/` modules, but `core/` modules know nothing about Flare, sockets, or channels. This separation is intentional and worth preserving as your app grows: it keeps your domain logic testable without booting a channel.

## Core Architecture

### Startup sequence (`Flare.Application`)

When your host app starts (because `:flare` is listed as a dependency, Flare's own `Application` module starts automatically as part of your supervision tree — you never call anything to "start" Flare manually), the following happens in order:

1.  **`Flare.Layout.init_cache/0`** — creates the ETS table `:flare_layout_cache` (`:set, :public, :named_table, read_concurrency: true`). This must exist _before_ the supervisor tree starts, because a channel could theoretically try to read from it the instant the endpoint accepts a connection.
2.  **Supervisor tree starts**, with three children under `strategy: :one_for_one`:
    -   `Flare.Registry` — a `Registry` mapping `user_id` strings to their `Flare.UserState` GenServer PID. Any code anywhere can find a user's process with `Registry.lookup(Flare.Registry, user_id)`.
    -   `Flare.UserSupervisor` — a `DynamicSupervisor` (`strategy: :one_for_one`) that supervises one `Flare.UserState` GenServer per connected user. If one user's state process crashes, no other user is affected.
    -   `Flare.PubSub` — a `Phoenix.PubSub` instance used for broadcasting global state changes between a single user's own open screens (e.g. cart count updates everywhere), and for `broadcast_to_screen` / `broadcast_to_topic` fan-out to many users.
3.  **`Flare.Layout.warm_cache/1`** — reads `router.registered_screens()` from your app's configured router and, for every screen with `use_cache true` (the default), reads its `layout/*.json` and `state/*.json` files from disk **once** and stores them in the ETS table. This step happens _after_ the supervisor starts (because it needs to read `Application.get_env(:flare, :router)`, which is only guaranteed set by the time your app's config has loaded) but **before** the Phoenix endpoint starts accepting WebSocket connections — so no channel can ever join before the cache is warm.

If any layout file is missing or malformed at this point, Flare **raises immediately at boot**, with a message telling you exactly which screen module and which expected file path failed — so you find out at `mix phx.server` startup, not when the first real user hits that screen in production.

### Two kinds of "state" you need to keep straight

This is the single most important mental model in Flare. There are two completely separate places state can live, and confusing them is the #1 source of bugs:

1.  **`Flare.UserState`** (a GenServer, one per connected `user_id`) — holds this user's **server-owned** variable values (anything prefixed `flare_`), persisted across screen navigation _within a session_, but NOT persisted to disk (it's pure in-memory cache with an idle timeout — see below). This is Flare's answer to "how do I remember the counter value when the user navigates away and comes back?" without hitting the database on every navigation.
2.  **`Flare.Layout`'s ETS cache** — holds ONLY the static, shared `layout/*.json` and `state/*.json` **template files**, decoded once from disk and (optionally) gzip-precompressed. It is never user-specific and is shared read-only across every connected user. It is the mechanism that makes joins fast (zero disk I/O per join once warm).

These two caches never mix. `UserState` never touches ETS; ETS never holds per-user data. This is enforced structurally, not just by convention — the functions that read/write each one (`Flare.UserState.get_all/1`, `Flare.UserState.save/2` vs. `Flare.Layout.load_files/2`) simply don't share any code path.

### `Flare.Socket` — the per-connection "conn" equivalent

Every `mount/2`, `handle_event/3`, and `handle_info/2` callback you write receives (or returns) a `%Flare.Socket{}` struct:

```elixir
defstruct [
  :user_id,        # String user ID, or nil for anonymous sessions
  :screen_module,  # Your screen module, e.g. MyApp.Screens.Home
  :screen_name,    # String screen name, e.g. "home"
  assigns: %{},    # flare_ / local_ prefixed state values
  commands: []     # Queued client-side commands for this event cycle
]

```

You never construct this struct yourself — Flare builds it during `Flare.Channel.do_join/4` and threads it through your callbacks. You mutate it via `assign/2` and `assign/3` (imported automatically when you `use Flare.Screen`):

```elixir
socket = assign(socket, :flare_count, 5)
socket = assign(socket, flare_count: 5, flare_name: "Ahmad")

```

Both forms return a **new** socket — the original is never mutated in-place (this is a pure functional data structure, same discipline as `Plug.Conn`).

## The Screen Lifecycle

Here is the exact sequence of events, end to end, every time a client joins `"flare:<screen_name>"`:

```
Client                          Flare.Channel                    Your Screen Module
  │                                    │                                  │
  │──── join("flare:home", params) ───►│                                  │
  │                                    │                                  │
  │                          [1] Check user_id is non-nil                 │
  │                              (set by UserSocket.connect/3)            │
  │                                    │                                  │
  │                          [2] Start/find UserState GenServer           │
  │                              (Flare.UserState.ensure_started/1)       │
  │                                    │                                  │
  │                          [3] Subscribe to PubSub topics:              │
  │                              "user:<user_id>"                        │
  │                              "screen:<user_id>:<screen_name>"        │
  │                              broadcast topic (default or custom)     │
  │                                    │                                  │
  │                          [4] Resolve screen module from router        │
  │                                    │                                  │
  │                          [5] Authorization check                      │
  │                              (authorize/2 or router roles:)          │
  │                                    │──── (rejected?) ───► {:error, %{"reason" => "unauthorized"}}
  │                                    │                                  │
  │                          [6] Restore saved_assigns from UserState,    │
  │                              scoped to this screen's declared        │
  │                              variable names + configured global_keys │
  │                                    │                                  │
  │                                    │──── mount(params, socket) ─────►│
  │                                    │                                  │ (query DB, assign values)
  │                                    │◄──── {:ok, new_socket} ─────────│
  │                                    │                                  │
  │                          [7] Build init envelope:                     │
  │                              layout JSON + variable defs + state     │
  │                                    │                                  │
  │◄──── {:ok, %{}} (join reply) ──────│                                  │
  │◄──── push "init" envelope ─────────│                                  │
  │                                    │                                  │
  │──── push "event" {type, payload} ─►│                                  │
  │                                    │──── handle_event/3 ─────────────►│
  │                                    │◄──── {:noreply, new_socket} ────│
  │                          [8] Diff old vs new assigns                  │
  │                          [9] Split diff into global_keys vs page-only │
  │                         [10] Save page-only diff to UserState         │
  │                         [11] Broadcast global-key diff via PubSub     │
  │◄──── push "patch" {state, commands} │                                  │
  │◄──── {:reply, :ok} to the push ────│                                  │
  │                                    │                                  │
  │──── (any process message, e.g. PubSub broadcast) ─────────────────────┤
  │                                    │──── handle_info/2 ──────────────►│
  │                                    │◄──── {:noreply, new_socket} ────│
  │◄──── push "patch" (if diff nonempty)│                                  │
  │                                    │                                  │
  │──── leave() / disconnect ──────────►│                                  │
  │                          [12] terminate/2 — save FULL current state   │
  │                              to UserState (safety net for the case    │
  │                              where a disconnect happens mid-event,    │
  │                              between diff-cycles)                    │

```

### The important subtleties

-   **Authorization always runs before mount.** No layout bytes, no state, nothing is ever sent to a client who fails `authorize/2` or the router's `roles:` check. The rejected client receives only `{"reason" => "unauthorized", "detail" => ...}`.
-   **`local_` prefixed keys never leave the client and never come from the server.** `Flare.Diff.compute/2` explicitly filters them out of every diff (`local_key?/1` checks `String.starts_with?(to_string(key), "local_")`). This is what makes `local_dark_mode`, `local_drawer_open`, and the per-action `local_flare_pending_<action>` locks safe: the server can `assign/3` a `local_` key all it wants and it will simply never be transmitted. Practically, this means you should never rely on the server to _read back_ a `local_` value either — it's a one-way, client- owned channel by design.
-   **`terminate/2` always saves full current assigns, not just the last diff.** If the connection drops mid-session (network blip, app backgrounded, tab closed), the last diffed `handle_event` call already incrementally saved the page-local half of any change to `UserState` via `push_diff_and_commands/3` — but `terminate/2` is a belt-and-suspenders save of the _entire_ current `assigns` map, so nothing is ever lost even if a save was somehow skipped.
-   **Presence tracking (for shared screens) happens strictly after authorization**, inside `do_mount`, never before. This prevents a rejected user's `user_id` from leaking into another screen's presence list.

## Creating a New Screen

### Minimal example

```elixir
# lib/my_app/flare_app/screens/welcome/welcome.ex
defmodule MyApp.FlareApp.Screens.Welcome do
  use Flare.Screen
  screen_dir __DIR__

  @impl true
  def mount(_params, socket) do
    {:ok, assign(socket, flare_title: "Welcome!")}
  end
end

```

```json
// lib/my_app/flare_app/screens/welcome/layout/welcome.json
{
  "card": {
    "log_id": "welcome_screen",
    "states": [
      {
        "state_id": 0,
        "div": {
          "type": "text",
          "text": "@{flare_title}",
          "font_size": 22
        }
      }
    ]
  },
  "templates": {}
}

```

```json
// lib/my_app/flare_app/screens/welcome/state/welcome.json
{
  "variables": [
    { "name": "flare_title", "type": "string", "value": "" }
  ]
}

```

Register it in your router:

```elixir
# lib/my_app/flare_app/flare_router.ex
defmodule MyApp.FlareApp.FlareRouter do
  use Flare.Router
  screen "welcome", MyApp.FlareApp.Screens.Welcome
end

```

That's the whole screen. `screen_dir __DIR__` is **mandatory** and must be called directly below `use Flare.Screen` — it tells Flare where to find this screen's `layout/` and `state/` subfolders (relative to the `.ex` file's own directory, using Elixir's compile-time `__DIR__`).

### The full `Flare.Screen` callback surface

```elixir
@callback mount(params :: map(), socket :: Flare.Socket.t()) ::
              {:ok, Flare.Socket.t()} | {:error, term()}

@callback handle_event(
              event   :: String.t(),
              payload :: map(),
              socket  :: Flare.Socket.t()
            ) :: {:noreply, Flare.Socket.t()}

@callback handle_info(message :: term(), socket :: Flare.Socket.t()) ::
              {:noreply, Flare.Socket.t()}

@callback authorize(user_id :: String.t(), params :: map()) ::
              :ok | {:error, term()}

@callback topic(user_id :: String.t(), params :: map()) :: String.t() | :default

```

Only `mount/2` is strictly required to matter for a useful screen (you technically get a `def mount(_p, s), do: {:ok, s}` overridable default if you don't define one, but that would render an empty static screen). The other four all have sensible no-op defaults injected automatically by `use Flare.Screen`:

```elixir
def authorize(_user_id, _params), do: :ok
def handle_event(_event, _payload, socket), do: {:noreply, socket}
def handle_info(_msg, socket), do: {:noreply, socket}
def topic(_user_id, _params), do: :default
def __use_cache__, do: true

```

All of these are `defoverridable`, so you only write the ones you actually need.

### `mount/2` — what it's for

Called exactly once per channel join. This is where you query the database, compute derived values, and `assign/2`/`assign/3` them onto the socket. Whatever you assign here becomes the **initial state** sent to the client in the `"init"` envelope.

```elixir
@impl true
def mount(_params, socket) do
  {:ok, counter} = CounterRecord.get_or_create_for_owner(socket.user_id)

  socket
  |> assign(:flare_count, counter.current_count)
  |> assign(:flare_last_updated, format_time(counter.last_updated_at))
  |> then(&{:ok, &1})
end

```

`mount/2` receives `params` — the join params dict the client sent (e.g. `{"code" => "AH7K2P"}` for a screen joined with a dynamic identifier), and `socket` — already populated with `socket.user_id` and any restored `saved_assigns` from `UserState` for this screen (scoped to this screen's own declared `flare_` variable names plus any configured `global_keys` — see [Global Keys](https://claude.ai/chat/594413f3-2e86-417b-b7bd-00ffdf283354#global-keys)).

### `handle_event/3` — reacting to taps and input

Called every time the client fires a `flare://action` (see [Layout JSON](https://claude.ai/chat/594413f3-2e86-417b-b7bd-00ffdf283354#layout-json--state-json-files) for how actions are wired in JSON). The `event` string is whatever `flare_action` value the layout's `action.url` query string set; `payload` is a map of any other query params on that same URL, expression-resolved by the client before sending.

```elixir
@impl true
def handle_event("increment", _payload, socket) do
  {:ok, counter} = CounterRecord.get_or_create_for_owner(socket.user_id)
  {:ok, updated} = CounterRecord.increment(counter)

  socket
  |> assign(:flare_count, updated.current_count)
  |> then(&{:noreply, &1})
end

```

You can match on multiple event clauses just like any Elixir function:

```elixir
def handle_event("go_back", _payload, socket), do: {:noreply, navigate(socket, "home")}
def handle_event("logout", _payload, socket), do: {:noreply, clear_storage(socket)}

```

Anything you `assign/2`/`assign/3` inside `handle_event/3` gets automatically diffed against the previous assigns and shipped to the client as a `"patch"` message — you never manually construct or send a patch. See [Diffing](https://claude.ai/chat/594413f3-2e86-417b-b7bd-00ffdf283354#the-diff-engine).

### `handle_info/2` — reacting to process messages

Fired for anything sent directly to this channel process — PubSub broadcasts, timers, results from async tasks you spawned, etc. Exactly the same diff-and-patch behavior as `handle_event/3` applies: whatever the assigns look like when this returns is diffed against what they were before, and the delta is pushed.

```elixir
@impl true
def handle_info(%Phoenix.Socket.Broadcast{event: "presence_diff"}, socket) do
  # re-derive something from Flare.Presence.list/1, assign it, done —
  # the diff/patch machinery handles the rest automatically
  {:noreply, socket}
end

# Always have a catch-all so unrelated messages don't crash the channel:
def handle_info(_msg, socket), do: {:noreply, socket}

```

### `authorize/2` — gating access

Return `:ok` to allow the join, `{:error, reason}` to reject it. This runs strictly before `mount/2`. Enforced entirely server-side; there is no client-side bypass possible, since the client receives nothing (no layout, no state) until this passes.

```elixir
@impl true
def authorize("guest_" <> _, _params), do: {:error, "Please create an account."}
def authorize(_user_id, _params), do: :ok

```

If a screen module defines its own `authorize/2`, it takes **full priority** over any `roles:` declared for that screen in the router — the router roles are skipped entirely. Use `roles:` for simple role checks declared in one place (the router); use `authorize/2` in the screen module itself for anything more custom (feature flags, time-of-day, IP checks, etc.).

### `topic/2` — opting into a shared/multi-user screen

By default, every screen uses one hardcoded broadcast topic per screen _name_ (`"broadcast:<screen_name>"`), which every user viewing that screen name shares — fine for screens like a global "sale is on" banner. But most screens are per-instance: a specific window/room/document identified by a parameter, where you want a broadcast topic _per instance_, not per screen-name. Override `topic/2` for that:

```elixir
@impl true
def topic(_user_id, params) do
  code = params["code"] || ""
  "window:#{String.upcase(code)}"
end

```

See [Shared / Multi-User Screens](https://claude.ai/chat/594413f3-2e86-417b-b7bd-00ffdf283354#shared--multi-user-screens-topic2-and-presence) for the full mechanics this unlocks (per-instance broadcasting + Presence).

### `use_cache` — ETS caching per screen

```elixir
defmodule MyApp.FlareApp.Screens.Welcome do
  use Flare.Screen
  screen_dir __DIR__
  use_cache false   # always read layout/state from disk, never cache in ETS
end

```

See the dedicated [ETS Layout Cache](https://claude.ai/chat/594413f3-2e86-417b-b7bd-00ffdf283354#the-ets-layout-cache--use_cache) section below for exactly what this controls and when to flip it.

## The Router

`Flare.Router` is a tiny DSL for mapping screen name strings to screen modules:

```elixir
defmodule MyApp.FlareApp.FlareRouter do
  use Flare.Router

  screen "welcome", MyApp.Welcome
  screen "profile", MyApp.Profile, roles: [:admin]
  screen "orders",  MyApp.Orders,  roles: [:admin, :staff]
  screen "account", MyApp.Account, roles: [:user, :admin]

  # Persistent scaffold regions are registered exactly the same way —
  # see the Scaffold section for what `scaffold:` on OTHER screens means.
  screen "bottom_bar", MyApp.Scaffold.BottomBar, region: :bottom_bar
end

```

Then wire it into config:

```elixir
config :flare, router: MyApp.FlareApp.FlareRouter

```

`Flare.Channel.do_join/4` calls `router.screen_for!(screen_name)` on every join to resolve which module handles a given topic. If a client joins a screen name that isn't registered, `screen_for!/1` **raises** with a message telling the developer exactly which line to add — this is a programmer error (a client requesting a nonexistent screen), not a runtime condition to silently swallow.

### `roles:` option

```elixir
screen "admin", MyApp.Admin, roles: [:admin]

```

Restricts a screen so only users whose resolved role is in the list can join. Everyone else gets `{"reason" => "unauthorized"}` — no mount, no layout, no state ever leaves the server. Flare calls your configured role resolver to determine the user's role:

```elixir
config :flare, role_resolver: {MyApp.Accounts, :get_role, 1}

```

The resolver is any `{module, function, arity}` accepting a `user_id` string and returning an atom role (or `nil` if unknown):

```elixir
defmodule MyApp.Accounts do
  def get_role("guest_" <> _), do: :guest
  def get_role(user_id) do
    case MyApp.Repo.get(MyApp.User, user_id) do
      %{role: role} -> String.to_existing_atom(role)
      nil           -> nil
    end
  end
end

```

If a screen declares `roles: [...]` but no `role_resolver` is configured at all, Flare **fails closed** — it denies access and logs a clear error telling you to add the config line. It will never silently treat an unconfigured resolver as "open to everyone."

If neither `roles:` nor a custom `authorize/2` is present, a screen is open to any _authenticated_ user (i.e. anyone who passed `UserSocket`'s token check, guests included).

### `scaffold:` option

```elixir
screen "home", MyApp.Home, scaffold: [:bottom_bar]

```

This is unrelated to access control — it tells the client which persistent scaffold regions should be visible while this particular screen is the active content. See [Scaffold Regions](https://claude.ai/chat/594413f3-2e86-417b-b7bd-00ffdf283354#scaffold-regions--the-multi-mount-architecture).

## State & Variables Deep Dive

### The `flare_` prefix — server-owned, synced state

Any assign whose key starts with `flare_` is:

-   Included in the `"init"` envelope's `"state"` field on first join.
-   Diffed on every `handle_event`/`handle_info` cycle; if it changed, it's included in the next `"patch"` message.
-   Persisted to this user's `Flare.UserState` GenServer, scoped per screen (see below), so it survives navigating away and back within the same session.
-   Visible in DivKit layout JSON as `@{flare_your_key}`.

This is the primary channel for server → client data flow. There is no naming requirement beyond the `flare_` prefix — `flare_count`, `flare_greeting`, `flare_watches` (an array), etc. are all valid.

### The `local_` prefix — client-owned, never synced

Any variable whose name starts with `local_` is understood by convention across both server and client to be **owned by the client**:

-   `Flare.Diff.compute/2` explicitly excludes `local_` keys from every diff, so the server literally cannot push a value for a `local_` variable to the client, even if you `assign(socket, :local_x, "y")` by mistake — it's simply invisible to the diffing/patching machinery.
-   The web and Android clients treat any `local_`-prefixed variable declared in a `state/*.json` file specially: on `"init"`, if that variable **already has a value in the global controller** (i.e. it was set earlier this session, e.g. by a previous screen or restored from `localStorage`), the client **skips re-registering it from the JSON file's default**. This is the exact mechanism that prevents, e.g., `local_dark_mode` from silently resetting to `false` every time a new screen's `state/*.json` (which necessarily declares a default) loads.
-   The reserved variable `local_flare_pending_<action>` (see [Pending-Action Locks](https://claude.ai/chat/594413f3-2e86-417b-b7bd-00ffdf283354#pending-action-locks-local_flare_pending_)) is a special case of this same pattern, entirely SDK-managed.

**Rule of thumb:** if a value should ever be "remembered" or shown differently per-device without a server round trip (dark mode toggle, drawer open/closed, an in-progress text input the user hasn't submitted yet), prefix it `local_`. If a value represents something the server knows and the client should merely display, prefix it `flare_`.

### `Flare.UserState` — the per-user GenServer

One GenServer process per connected user, keyed by `user_id` in `Flare.Registry`. Its entire job is to be an in-memory cache of the user's current `flare_`-prefixed assign values, so that:

1.  Navigating from screen A to screen B and back to screen A doesn't require re-querying the database for values screen A already knew moments ago.
2.  A "global" value changed on one screen (e.g. cart item count) can be instantly reflected on every other currently-open screen for that same user, without any of them needing to poll or refetch.

Its internal state is a flat map: `%{user_id: user_id, data: %{}}`. Public API:

```elixir
Flare.UserState.ensure_started(user_id)      # idempotent — starts if not running
Flare.UserState.get_all(user_id)             # returns the entire cached map
Flare.UserState.save(user_id, values)        # page-local save, no broadcast
Flare.UserState.update(user_id, new_values)  # global save, broadcasts diff via PubSub
Flare.UserState.invalidate(user_id, keys)    # drop specific keys (reload on next access)
Flare.UserState.stop(user_id)                # graceful shutdown, e.g. on logout

```

`save/2` vs `update/2` is the mechanism behind page-local vs. global keys (see next section) — `save/2` is used internally by `push_diff_and_commands/3` for the page-scoped half of a diff (no broadcast, since only the current screen cares); `update/2` is used for the `global_keys`-scoped half (broadcasts via `Flare.PubSub` on topic `"user:<user_id>"`, which every one of this user's _other_ open screens is subscribed to — this is exactly how a value changed on screen A instantaneously updates screen B without any polling).

Both `save/2` and `update/2` treat a `nil` value as an intentional _removal_ — the key is dropped from the cache entirely rather than stored as `nil`. Values are also filtered: `save/2` only accepts keys with the `flare_` prefix (protecting against accidentally persisting internal Phoenix assigns or anything else that shouldn't be there).

**Idle timeout.** If no message arrives for a `Flare.UserState` process within `user_state_timeout` milliseconds (default `300_000` = 5 minutes, configurable via `config :flare, user_state_timeout: ...`), the GenServer shuts itself down cleanly. The _next_ channel join for that user simply starts a fresh one via `ensure_started/1` — this is invisible to the developer and to the user; it's purely a memory-reclamation mechanism for users who've been inactive.

### Global keys

```elixir
config :flare,
  global_keys: [:flare_overlay_visible, :flare_active_tab]

```

Any assign key listed here is treated specially by `Flare.Channel.push_diff_and_commands/3`:

1.  It's split out of the diff separately from all other (page-local) changed keys.
2.  It's saved via `Flare.UserState.update/2` (which broadcasts).
3.  Every other currently-open channel for this same user, on receiving that broadcast (`{:state_update, diff}` on topic `"user:<user_id>"`), merges it into their own assigns and immediately pushes a `"patch"` to their client too.

This is how, e.g., a bottom-bar's `flare_active_tab` (which button is highlighted) stays in sync between the bottom_bar scaffold region and whatever content screen is currently active — both are technically different channel processes, but they're both subscribed to the same user's PubSub topic and both react to the same global-key broadcast.

Everything **not** listed in `global_keys` is page-local: saved to `UserState` via `save/2` (no broadcast), and only pushed to the one channel that changed it.

On `mount/2`, a screen's `saved_assigns` restoration is scoped to _that screen's own declared `flare_` variable names_ (read from its `state/<screen>.json`) **plus** whatever's listed in `global_keys` — this is deliberate: it prevents one screen's leaked keys/values (e.g. a large list only screen A ever populated) from silently bleeding into screen B's initial state just because they happen to share a `UserState` process. See `Flare.Layout.declared_variable_names/2` and its use inside `Flare.Channel.do_mount/5`.

### The Diff engine

`Flare.Diff` is a small, pure module — three functions, zero side effects, zero process communication:

```elixir
Flare.Diff.compute(old_assigns, new_assigns)
# Returns only what changed: local_ keys excluded, removed keys included as nil

Flare.Diff.empty?(diff)
# true if map_size(diff) == 0 — used to skip sending empty "patch" messages entirely

Flare.Diff.split(diff, global_keys)
# {global_diff, page_diff} — the mechanism behind the global_keys feature above

```

`compute/2` semantics, precisely:

-   A key present in `new` with a value different from `old` (or absent from `old`) → included in the diff **with its new value**.
-   A key present in `old` but absent from `new` → included in the diff **with value `nil`** (this signals "removed" to the client, which then drops that variable — see `_handlePatch` in the web client).
-   An unchanged key → excluded (keeps wire messages tiny — a patch after tapping "+1" on a counter screen is typically a handful of bytes).
-   Any `local_`-prefixed key on either side → always excluded, regardless of whether it changed.

## Layout JSON & State JSON Files

### File placement

Every screen expects exactly this structure relative to the directory declared by `screen_dir __DIR__`:

```
<screen_dir>/
├── layout/
│   └── <screen_name>.json     ← REQUIRED — the DivKit card
└── state/
    └── <screen_name>.json     ← OPTIONAL — variable type definitions

```

`<screen_name>` must match exactly what you registered in the router (`screen "home", ...` expects `layout/home.json`). If the layout file is missing, Flare raises at ETS-warm-time (for `use_cache true` screens) or at first-join time (for `use_cache false` screens) with the exact expected path.

The state file is genuinely optional — a screen with zero server-side variables (pure navigation/static content) doesn't need one; Flare defaults to `%{"variables" => []}` if the file is absent.

### `layout/<screen>.json` — the DivKit card

This is a plain [DivKit](https://divkit.tech/) card. Flare doesn't impose any schema on top of DivKit's own — every element type, container, gallery, input, image, gradient, corner radius, etc. that DivKit supports works exactly as DivKit documents it. Flare's only contribution is the expression syntax for binding to your server-side variables (`@{flare_your_key}`) and the `flare://action` URL convention for wiring taps to server events (see below).

```json
{
  "card": {
    "log_id": "counter_screen",
    "states": [
      {
        "state_id": 0,
        "div": {
          "type": "container",
          "orientation": "vertical",
          "items": [
            {
              "type": "text",
              "text": "@{flare_count}",
              "font_size": 72
            },
            {
              "type": "text",
              "text": "+",
              "action": {
                "log_id": "btn_plus",
                "url": "flare://action?flare_action=increment"
              }
            }
          ]
        }
      }
    ]
  },
  "templates": {}
}

```

### Wiring taps to server events: `flare://action`

Every actionable element (a text with an `action`, a container with an `action`, etc.) uses this URL scheme:

```
flare://action?flare_action=<event_name>&param1=value1&param2=value2

```

-   `flare_action` is **required** and becomes the `event` string your `handle_event/3` matches on.
-   Any additional query params become keys in the `payload` map passed to `handle_event/3`.
-   Values can (and usually should) be DivKit expressions themselves, so dynamic data flows through:

```json
"action": {
  "log_id": "btn_check",
  "url": "flare://action?flare_action=preview_code&code=@{encodeUri(local_code_input)}"
}

```

DivKit fully resolves the expression (including function calls like `encodeUri()`, and even `item_builder` loop scope variables) **before** the URL ever reaches the client SDK's action handler — so by the time your `handle_event("preview_code", %{"code" => code}, socket)` runs, `code` is already the resolved, percent-decoded string. Neither the web nor Android client does any manual expression parsing for this path — see `_parseFlareActionUrl` in the web client and `parseFlareActionUrl` in `FlareDivActionHandler.java` on Android; both are simple query-string readers, nothing more, because DivKit already did the resolution work.

> **Legacy note:** an older convention put dynamic values in the DivKit `action.payload` object instead of the URL query string. This still works (both clients resolve `@{varName}` strings found in top-level `payload` keys via a fallback resolver), but DivKit **never** expression-resolves `payload` on any platform (it's schema-typed as an opaque object), so the client SDK has to do that resolution itself with a plain string-matching regex, which is strictly less robust than the URL-param path. **Prefer URL query params for all new screens.**

### `state/<screen>.json` — variable declarations

```json
{
  "variables": [
    { "name": "flare_count",        "type": "integer", "value": 0 },
    { "name": "flare_last_updated", "type": "string",  "value": "" },
    { "name": "local_code_input",   "type": "string",  "value": "" },
    { "name": "local_flare_pending_confirm_watch", "type": "boolean", "value": false }
  ]
}

```

Each entry needs a `name`, a `type` (`"string"`, `"integer"`, `"number"`, `"boolean"`, `"array"`, or `"dict"`), and a `value` used as the initial default before the server's `mount/2` values are layered on top.

This file has two consumers:

1.  **The client SDK**, which registers each variable with DivKit's global variable controller before rendering the layout, so every `@{...}` expression in the layout has something to bind to from the very first frame (no flash of unbound/undefined variables).
2.  **`Flare.Layout.declared_variable_names/2`**, used server-side to scope what a screen's `mount/2` is allowed to restore from `UserState` — see [Global Keys](https://claude.ai/chat/594413f3-2e86-417b-b7bd-00ffdf283354#global-keys) above.

### Field types you can bind

DivKit expressions support arithmetic, string concatenation, ternaries, comparisons, and a decent function library (`len()`, `getStringFromDict()`, `encodeUri()`, and more — see the `EXPRESSION_RESOLUTION.md` file bundled in `flare/` for the full cross-platform expression-resolution contract both clients implement identically). A few patterns you'll use constantly:

```json
"visibility": "@{flare_count == 0 ? 'visible' : 'gone'}"
"text_color": "@{local_dark_mode ? '#ffffff' : '#000000'}"
"text": "@{flare_status == 'open' ? '🟢 Open' : '⚪ Closed'}"

```

### Repeating lists — `item_builder`

For rendering an array (`type: "array"` in state JSON) as repeated UI, use DivKit's `item_builder`:

```json
{
  "type": "container",
  "item_builder": {
    "data": "@{flare_watches}",
    "data_element_name": "watch_item",
    "prototypes": [
      {
        "div": {
          "type": "text",
          "text": "@{getStringFromDict(watch_item, 'name')}"
        }
      }
    ]
  }
}

```

`flare_watches` is assigned server-side as a plain list of maps (Flare stringifies keys for the wire, so build the maps with string keys, e.g. `%{"name" => "...", "code" => "..."}`), and `data_element_name` gives you the per-item loop variable name to reference inside the prototype.

## The ETS Layout Cache & `use_cache`

Every screen's `layout/*.json` and `state/*.json` files are, by default (`use_cache true`), loaded into RAM **once**, at application startup, via `Flare.Layout.warm_cache/1`. Every subsequent channel join for that screen reads straight from ETS — **zero disk I/O at runtime**, regardless of how many users join that screen concurrently.

```elixir
defmodule MyApp.Welcome do
  use Flare.Screen
  screen_dir __DIR__
  use_cache false   # always read fresh from disk on every join
end

```

Set `use_cache false` **only** when you need to see layout changes take effect without restarting the server — i.e. during active local development of that specific screen's JSON. It only affects that one screen; every other screen in your app still uses ETS normally. `use_cache false` screens:

-   Always read directly from disk on every join, bypassing ETS entirely.
-   Never get gzip-precompressed (see [optimize](https://claude.ai/chat/594413f3-2e86-417b-b7bd-00ffdf283354#the-binary-protocol--optimize) — they always send plain JSON, never the binary frame format, regardless of your `optimize` setting).

**Convention used throughout the shipped template and reference app:** screens under active development are `use_cache false`; stable, rarely-changing screens (home, static content, scaffold regions) are left at the `use_cache true` default. Flip screens back to `true` before shipping to production — every disk read avoided is real latency saved under load.

### Hot layout updates without a restart

If you need to push a _fresh_ layout to already-connected users (e.g. after a deploy that only changed JSON, no server logic), call:

```elixir
Flare.update_layout(user_id, screen_name)

```

This always bypasses ETS and reads the current file fresh from disk (regardless of that screen's `use_cache` setting), pushes a `"layout_update"` message to that one user's open channel for that screen (the client swaps the rendered DivKit view while **preserving current variable values**, so the user doesn't lose their in-progress state), and — if the screen normally uses ETS — refreshes the ETS entry too, so any _new_ joins after this point also get the updated layout.

### Manual cache invalidation

```elixir
Flare.Layout.invalidate(screen_name)

```

Deletes one screen's ETS entry. Not needed for normal deploys (a node restart clears ETS automatically via the startup `warm_cache` re-run), but useful if you're editing a layout file on a live node without going through `Flare.update_layout/2` — the _next_ join for that screen will read from disk and repopulate the cache. There's also a defensive fallback built in: if `Flare.Layout.load_files_from_ets/2` ever gets a genuine ETS miss (shouldn't happen after a normal warm-up, but could if the table was cleared manually), it logs an error, reads from disk once, and repopulates — a one-time self-healing recovery rather than a hard crash.

## Commands (Server → Client Instructions)

Commands are instructions from the server to the client SDK, processed **in order, after** state changes are applied for that same event/patch cycle. They deliberately keep control flow (navigation, alerts, storage) separate from data (`flare_`/`local_` state) — Flare's design philosophy here explicitly rejects the alternative pattern of "set a `redirect_to` variable and watch for it client-side," because that mixes control flow with data, creates race conditions, and is hard to debug.

All command builders live in `Flare.Commands` (auto-imported by `use Flare.Screen`), accept a socket, and return a new socket — they chain naturally with the pipe operator:

```elixir
socket
|> assign(:flare_auth_success, true)
|> store_token(token)
|> navigate("store")
|> haptic(:success)

```

### `navigate/3`

```elixir
navigate(socket, "store")
navigate(socket, "product", %{product_id: "prod_123"})

```

Tells the client to leave the current channel and join a new one. This is the **only** way screens navigate in Flare — there's no server-side redirect concept, because the client owns its own channel lifecycle.

### `show_alert/4`

```elixir
show_alert(socket, "Are you sure?", "This action cannot be undone.", "Delete")

```

Native platform alert dialog (`window.alert`-style on web, `AlertDialog` on Android).

### `store_token/2`

```elixir
socket |> store_token(Phoenix.Token.sign(MyApp.Endpoint, "user_auth", user_id))

```

Tells the client to persist an auth token securely:

-   **Web:** server-side session (never `localStorage`) — actually, per the current web client implementation, it's stored via `localStorage` (`flare_token`) since there's no server-side session concept wired up by default; check `_executeCommand`'s `"store_token"` case if you need to change this for your own security requirements.
-   **iOS:** Keychain (not yet implemented — see [iOS](https://claude.ai/chat/594413f3-2e86-417b-b7bd-00ffdf283354#ios-client)).
-   **Android:** `SharedPreferences` (`PREF_TOKEN` key) via the Flare Android SDK.

### `clear_storage/1`

```elixir
socket |> clear_storage()

```

Clears the stored auth token — the client's job on receiving this is to reconnect as anonymous on the next app open. This is exactly how logout is implemented in every screen you'll see in the shipped template (`handle_event("logout", _payload, socket), do: {:noreply, clear_storage(socket)}`).

### `haptic/2`

```elixir
socket |> haptic()          # :success (default)
socket |> haptic(:error)

```

Valid styles: `:success`, `:warning`, `:error`, `:light`, `:medium`, `:heavy`.

### `hide_scaffold/2` and `show_scaffold/2`

```elixir
socket |> hide_scaffold(:bottom_bar)
socket |> show_scaffold(:bottom_bar)

```

Runtime overrides for one scaffold region (`:bottom_bar`, `:top_bar`, `:drawer`, `:end_drawer`), without changing the screen's declared default `scaffold:` list in the router. Useful for transient states — e.g. hiding the bottom bar while a full-screen modal-like flow is active on the current screen, then re-showing it afterward.

## Authentication & Tokens

**Flare itself never issues tokens or creates identities.** This is a hard architectural boundary, stated explicitly in `Flare.UserState`'s own moduledoc: token issuance (`/auth/login`, `/auth/register`, `/auth/guest`) is entirely the _host application's_ responsibility. Flare's only job is to **verify** whatever token the host app already issued, inside the host app's own `UserSocket.connect/3` callback, and gate every channel join on a non-nil `user_id` assign.

### The reference implementation (JWT via Joken)

The shipped template implements this pattern:

**1. Token issuance/verification (`Core.Accounts.AuthToken`)** — uses `Joken.Config` with an `HS256` signer keyed off a configured secret:

```elixir
config :my_app, jwt_secret: "CHANGE_ME_TO_A_LONG_RANDOM_SECRET"

```

```elixir
def generate_token(user_id, max_age_seconds) do
  generate_and_sign(
    %{"sub" => user_id, "exp" => Joken.current_time() + max_age_seconds},
    signer()
  )
end

def verify_token(token) do
  case verify_and_validate(token, signer()) do
    {:ok, %{"sub" => user_id}} -> {:ok, user_id}
    {:error, reason}           -> {:error, reason}
  end
end

```

**2. Auth HTTP endpoints (`Http.Controllers.AuthController`)**, wired under `/auth/*` in the plain (non-Flare) HTTP router:

```elixir
scope "/auth" do
  pipe_through :api
  post "/login",    AuthController, :login
  post "/register", AuthController, :register
  post "/guest",     AuthController, :guest
end

```

-   `POST /auth/login` — verifies email/password against `Core.Accounts.User.authenticate/2` (which delegates to `Identity`, a separate schema that decouples "who someone is" from "how they log in" — see below), then issues a JWT with `max_age: 86_400` (24 hours).
-   `POST /auth/register` — creates a `User` + a `"password"` `Identity` row in one transaction, then issues the same 24h token.
-   `POST /auth/guest` — generates a random guest ID (`"guest_" <> Base.encode16(:crypto.strong_rand_bytes(8), case: :lower)`) with **no** corresponding database row at all, and issues a token with `max_age: 2_592_000` (30 days). Guests are first-class citizens throughout Flare — `user_id` is just a string, and a `"guest_"` prefix is the only convention distinguishing them (used e.g. in `get_role/1` clauses and `authorize/2` clauses that block guests from certain screens).

**3. Socket-level verification (`Http.UserSocket`)** — this is the piece that actually satisfies Flare's contract:

```elixir
defmodule MyApp.Http.UserSocket do
  use Phoenix.Socket
  channel "flare:*", Flare.Channel

  @impl true
  def connect(%{"token" => token}, socket, _connect_info) do
    case MyApp.Core.Accounts.AuthToken.verify_token(token) do
      {:ok, user_id} -> {:ok, assign(socket, :user_id, user_id)}
      {:error, reason} ->
        if expired_error?(reason),
          do: {:error, %{reason: "session_expired"}},
          else: {:error, %{reason: "invalid_token"}}
    end
  end

  # No token at all = hard reject
  @impl true
  def connect(_params, _socket, _connect_info) do
    {:error, %{reason: "authentication_required"}}
  end
end

```

`assign(socket, :user_id, user_id)` here is the exact assign `Flare.Channel.join/3` later reads via `channel_socket.assigns[:user_id]` to decide whether to reject the join outright. If your `UserSocket` doesn't set this, **every** channel join fails with `"authentication_required"` and Flare logs an explicit error naming your `UserSocket` module as the thing to fix.

The `expired_error?/1` check is a loose `inspect/1` string match (Joken's error shape varies by version) — both `"session_expired"` and `"invalid_token"` map to the same client-side behavior (redirect to login), but are distinguished in logs/telemetry if you want to handle them differently.

### Security properties inherited from `Phoenix.Token`/JWTs (know these)

Documented explicitly in `Flare.UserState`'s moduledoc, because they're easy to get wrong:

-   **Tokens are signed, not encrypted.** Anyone holding a token can decode and read its payload (the `user_id`) in plaintext. The signature only prevents forgery/tampering — **never** put secrets (passwords, payment info) inside the token payload itself.
-   **Tokens have no revocation mechanism.** Once issued, a token stays valid until it expires (`max_age`), even if the user logs out, is banned, or changes their password elsewhere. `clear_storage/1` only removes the token from the _client device_ — a copy that leaked, or was captured before logout, remains valid until natural expiry.
-   If you need revocation or shorter-lived sessions, add a denylist check inside your own `UserSocket.connect/3` (Redis, ETS, or a DB table of revoked token IDs/timestamps), rejecting the connect if the token predates a "logout everywhere" timestamp for that user. This is intentionally left to the host app since storage requirements vary (ETS is fine single-node; multi-node deployments need a shared store).

### `Core.Accounts.Identity` — decoupling login method from profile

The template splits "who someone is" (`User` — email, role, display name) from "how they log in" (`Identity` — one row per linked auth method: `provider` = `"password"` today, with `"google"`/`"apple"`/`"keycloak"` straightforward to add later as additional `Identity` rows with **zero** changes to the `User` schema or existing data):

```elixir
schema "identities" do
  field :user_id, :binary_id
  field :provider, :string        # "password" | "google" | "apple" | ...
  field :provider_uid, :string    # lowercased email for password; OAuth sub for others
  field :credential, :string      # pbkdf2 hash for password; unused for OAuth
end

```

`unique_index(:identities, [:provider, :provider_uid])` gives you one row per (provider, external-id) pair — e.g. one row per email/password combination, or one row per linked Google account. Passwords are hashed with `Pbkdf2` (`pbkdf2_elixir`), not stored raw or with a weaker hash.

## Scaffold Regions & the Multi-Mount Architecture

Most real apps have persistent chrome around the "current screen" — a bottom tab bar, a top bar, side drawers, a global toast/overlay. Flare calls these **scaffold regions**, and they're implemented as ordinary Flare screens (own `.ex` module, own `layout/`/`state/`), just joined and kept alive differently by the client.

### Server side: registering a scaffold region

```elixir
# Router
screen "bottom_bar", MyApp.Scaffold.BottomBar, region: :bottom_bar

```

```elixir
defmodule MyApp.Scaffold.BottomBar do
  use Flare.Screen
  screen_dir __DIR__
  use_cache true

  @impl true
  def mount(_params, socket) do
    {:ok, assign(socket, flare_bottom_bar_visible: true, flare_active_tab: "home")}
  end

  @impl true
  def handle_event("tab_tap", %{"tab" => tab}, socket) do
    socket
    |> assign(:flare_active_tab, tab)
    |> navigate(tab)                # navigate/3 targets the CONTENT mount, always
    |> then(&{:noreply, &1})
  end
end

```

Note `flare_active_tab` is exactly the kind of value you'd put in `global_keys` — the bottom bar assigns it, but the _content_ screen (or another scaffold region) may want to reflect the same value too.

### Content screens opt into which regions they show

```elixir
# Router
screen "home",    MyApp.Screens.Home,    scaffold: [:bottom_bar]
screen "profile", MyApp.Screens.Profile, scaffold: [:bottom_bar, :top_bar]
screen "onboarding", MyApp.Screens.Onboarding, scaffold: []   # hide everything

```

-   `scaffold: [...]` on a screen → only those listed regions are visible while this screen is the active content; every other scaffold region (from the client's configured full list) is hidden.
-   **Omitting `scaffold:` entirely (`nil`)** → the client leaves whatever scaffold visibility it currently has untouched. This is deliberate: it's what keeps every screen written _before_ you adopted the scaffold feature behaving exactly as it did before, with zero migration required.
-   `scaffold: []` explicitly → hide every scaffold region for this screen.

`nil` vs `[]` is meaningfully different and both are legitimate — see the comment in `Flare.Channel.get_router_scaffold/2` for the exact reasoning.

### Client side: the Mount abstraction

Both the web and Android clients implement the identical concept of a **Mount** — an independent unit with its own container element, its own Phoenix channel, its own screen name, and its own set of in-flight pending-action locks:

-   **`content`** — the primary mount. Only `navigateTo()` (triggered by `navigate/3` commands from the server, browser back/forward, or Android back button) ever swaps its channel.
-   **One mount per configured persistent region** (`bottom_bar`, `top_bar`, `drawer`, `end_drawer`, `overlay`, or any subset you configure) — joined **once**, right after the socket opens, and **never left** for the life of the session. A tap in flight on the bottom bar can never block a tap on the main content screen, and vice versa, because each mount tracks its own pending-action set completely independently.

Web client config (in `index.html`):

```js
window.__flare__ = {
  wsUrl: "/socket",
  entryScreen: "home",
  persistentScreens: [
    { screen: "bottom_bar", region: "bottom_bar" }
  ],
  scaffoldRegions: ["bottom_bar"]
};

```

`persistentScreens` is what actually gets joined-once-and-kept-alive. `scaffoldRegions` is the subset that participates in per-screen visibility toggling driven by the router's `scaffold:` list — a region can be persistent without being scaffold-toggleable (the `overlay` region, for instance, self-governs its own visibility via its own `flare_overlay_visible` variable rather than being shown/hidden by the router's `scaffold:` mechanism — see the shipped `Overlay` scaffold module for the canonical example of this pattern: a server-driven, database-backed, one-time-per-user announcement system).

### The `overlay` region pattern (worth calling out specifically)

Unlike `bottom_bar`/`top_bar`/`drawer`/`end_drawer`, an `overlay` region is typically used for full-screen server-pushed takeovers — a welcome message, a forced maintenance notice, etc. — that are **not** part of the router's per-screen `scaffold:` toggling list at all. Instead, the overlay module itself decides its own visibility entirely in `mount/2`, by querying a "have I shown this to this user before" table:

```elixir
def mount(_params, socket) do
  case next_unseen(socket.user_id) do
    nil -> assign(socket, flare_overlay_visible: false, flare_message: "")
    %{message: message} -> assign(socket, flare_overlay_visible: true, flare_message: message)
  end
  |> then(&{:ok, &1})
end

def handle_event("dismiss", _payload, socket) do
  # mark as seen in the DB so it never shows again for this user
  {:noreply, assign(socket, :flare_overlay_visible, false)}
end

```

Because this is 100% server-decided and DB-backed (never cached, never client-side), it's trivially safe to add a new one-time announcement by just appending an entry to a list in the module — no migration, no new module, and it fires correctly even for a user reconnecting from a totally different device.

## Shared / Multi-User Screens (`topic/2` and Presence)

By default, every user viewing screen `X` shares one broadcast topic: `"broadcast:X"`. That's fine for a "global sale banner," but wrong for anything scoped to a specific instance (a specific chat room, a specific shared document, a specific physical location's live queue counter) — you don't want every "counter" screen in your entire app broadcasting to every other, unrelated counter's viewers.

Override `topic/2` to scope broadcasts to a specific instance identified by a join param:

```elixir
@impl true
def topic(_user_id, params), do: "window:#{params["code"]}"

```

Now every viewer who joined this screen with the _same_ `code` param shares one topic (`"broadcast:window:AH7K2P"`, since `Flare.Channel` always prefixes custom topics with `"broadcast:"`); viewers with a different `code` are completely isolated from each other, on entirely separate topics.

### Broadcasting to that scoped topic

```elixir
Flare.broadcast_to_topic("window:#{code}", %{flare_count: new_count})

```

Every currently-joined viewer of that exact instance receives a `"patch"` with the diff — this is the mechanism behind, e.g., a "controller" (the owner, tapping +/− buttons) instantly updating every "viewer" (anyone else watching that same window/instance) in real time, with no polling on either side.

### Presence — knowing who's currently viewing a shared instance

Because a screen that overrides `topic/2` is, by definition, a "shared screen" (potentially many users on the same logical instance), Flare automatically tracks presence for it via `Flare.Presence` (a thin `Phoenix.Presence` wrapper), **but only after authorization has passed**, inside `do_mount` — this is important: tracking before authorization would leak a rejected user's `user_id` into the presence list of a screen they were never actually allowed to join.

Screens using the default topic (i.e. never overriding `topic/2`) are never presence-tracked at all — zero extra overhead, nothing exposed, for the vast majority of screens that don't need this.

To react to presence changes (e.g. show "controller is online" to viewers), listen for the standard Phoenix Presence broadcast in `handle_info/2`:

```elixir
@impl true
def handle_info(%Phoenix.Socket.Broadcast{event: "presence_diff"}, socket) do
  code     = socket.assigns[:flare_code]
  owner_id = socket.assigns[:flare_owner_id]

  shared_topic = "broadcast:window:#{code}"
  is_online = Map.has_key?(Flare.Presence.list(shared_topic), owner_id)

  {:noreply, assign(socket, :flare_owner_online, is_online)}
end

```

Note the `"broadcast:"` prefix on the topic passed to `Flare.Presence.list/1` — this must exactly match the topic Flare's own presence-tracking call used internally (`Flare.Channel.do_mount/5`), which always prepends `"broadcast:"` to whatever your `topic/2` returned.

## Server-Initiated Pushes (Broadcasting APIs)

`Flare`'s public module (`lib/flare.ex`) exposes functions you can call from _anywhere_ in your application — a background job, LiveDashboard, an external webhook handler, a cron task — to push updates to connected clients without them having initiated anything.

### `Flare.push_to_user/3`

```elixir
Flare.push_to_user("user_123", "store", %{flare_cart_count: 4})

```

Pushes a state change to one specific user's one specific open screen. If that user isn't connected, or doesn't have that screen open, this is a silent no-op (returns `:ok` regardless) — it's a best-effort push, not a queued/durable message.

### `Flare.push_command_to_user/4`

```elixir
Flare.push_command_to_user("user_123", "store", "show_alert", %{
  title: "Order shipped!",
  message: "Your order is on the way."
})

```

Same idea, but pushes a single command (see [Commands](https://claude.ai/chat/594413f3-2e86-417b-b7bd-00ffdf283354#commands-server--client-instructions)) instead of a state diff.

### `Flare.update_layout/2`

```elixir
Flare.update_layout("user_123", "store")

```

Covered in [ETS Layout Cache](https://claude.ai/chat/594413f3-2e86-417b-b7bd-00ffdf283354#hot-layout-updates-without-a-restart) — hot-reloads one user's one screen's layout after a deploy, preserving current variable values.

### `Flare.broadcast_to_screen/2`

```elixir
Flare.broadcast_to_screen("store", %{flare_sale_active: true})

```

Broadcasts a state change to **every** user currently viewing screen name `"store"` (i.e. every viewer on the default, non-scoped topic). Good for global events: flash sales, site-wide announcements, live counters that genuinely are shared across all viewers of that screen.

### `Flare.broadcast_to_topic/2`

```elixir
Flare.broadcast_to_topic("window:AH7K2P", %{flare_count: 4})

```

Covered above — the instance-scoped counterpart to `broadcast_to_screen/2`, used with screens that override `topic/2`.

## The Binary Protocol & `optimize`

```elixir
config :flare, optimize: true

```

By default (`optimize: false`), every message Flare sends is a normal Phoenix JSON text frame — simplest to debug, no special handling needed.

When you turn `optimize: true` on, `Flare.Serializer` (a custom `Phoenix.Socket.Serializer`) changes behavior **only** for the two event types that can carry large payloads — `"init"` and `"layout_update"` (a DivKit layout JSON can easily be 60KB+ before compression). For those two events only, and only when the underlying cache entry was actually pre-compressed (i.e. the screen is `use_cache true` **and** was warmed with `optimize: true` already in effect at startup), it switches to a binary WebSocket frame instead of text.

### Why this exists

Embedding gzip-compressed bytes inside a JSON string requires base64 encoding, which adds ~33% size overhead on top of whatever gzip already saved. Sending raw compressed bytes in a binary WebSocket frame avoids that base64 tax entirely.

### Binary frame format (version 1)

```
[1 byte ] version        = 1
[4 bytes] header_len      big-endian uint32
[N bytes] header_json     compact JSON — screen, state, commands, encoding marker
[4 bytes] layout_len      big-endian uint32
[M bytes] layout_gz       gzip-compressed layout JSON bytes
[4 bytes] vars_len        big-endian uint32
[P bytes] vars_gz         gzip-compressed variables JSON array bytes

```

The header is deliberately left **uncompressed** — it's tiny (roughly 50 bytes) and the client needs to read it immediately to know how to interpret the rest of the frame. Layout and variables are compressed **independently**, so the client can decompress both in parallel (the web client does this via `Promise.all` and the native `DecompressionStream("gzip")` API — no external gzip library dependency needed in the browser).

### When compression actually happens

Compression happens **exactly once**, at `warm_cache/1` time (application startup), never per-request:

```elixir
layout_gz = layout_json |> Jason.encode!() |> :zlib.gzip()
vars_gz   = variables   |> Jason.encode!() |> :zlib.gzip()

```

These compressed binaries are stored directly in the ETS entry alongside the plain decoded maps. Every subsequent join for that screen reads the pre-compressed binary straight out of ETS and hands it to the serializer, which writes it to the wire as-is — **zero repeated compression work per request**, no matter how many users join.

### Compatibility guarantees

-   `use_cache false` screens are always tagged `:plain` in the cache (never compressed, regardless of `optimize`), so they're completely unaffected by this feature — they always take the plain JSON text path.
-   With `optimize: false` (the default), the serializer sends **every** message — including init/layout_update — as normal JSON text, byte-for- byte identical to Flare's behavior with no serializer customization at all.
-   Client→server messages are **never** binary — only server→client init/layout_update frames are. The existing text JSON decoder handles every client-originated message unconditionally.
-   A malformed or version-mismatched binary frame is caught client-side and falls back to an inline error message — never a silent crash, never leaked partial data.

Turn `optimize: true` on once your layouts are stable and you're optimizing for production bandwidth/latency; leave it `false` during active development if you find the binary frames make browser devtools network inspection less convenient (text frames are trivially readable in devtools; binary frames aren't, without writing a small decoder).

## The Web Client

Lives in `flare-web-client/`, a small esbuild-bundled JS app. Core file: `src/js/flare-client.js`, exporting `FlareClient`.

### Bootstrap

```html
<script>
  window.__flare__ = {
    wsUrl: "/socket",
    token: null,
    entryScreen: "home",
    persistentScreens: [
      { screen: "bottom_bar", region: "bottom_bar" }
    ],
    scaffoldRegions: ["bottom_bar"]
  };
</script>

```

`index.html` also contains the login/register/guest UI (a small vanilla-JS form, no framework), which calls `POST /auth/login`, `/auth/register`, or `/auth/guest`, stores the returned token in `localStorage`, then boots `FlareClient` with that token.

### What it does, end to end

-   Opens one Phoenix `Socket` with a custom binary-aware `decode` function (handles both plain text frames and the `optimize: true` binary frame format described above).
-   On socket open, joins every configured `persistentScreens` entry once and never leaves them (mirrors the server's scaffold concept exactly).
-   Registers DivKit's `createGlobalVariablesController()` **once**, shared across every mount — this is what makes `local_dark_mode` set by a tap on the top bar instantly reflected on the content screen, the bottom bar, and any drawer, with zero extra plumbing.
-   On `navigateTo(screenName, params)`, leaves the current content channel, joins the new one, and — while waiting — shows a Lottie transition overlay with the **old screen still visible underneath** (slides the new screen in over it once init arrives, rather than showing a jarring blank flash).
-   Intercepts a small set of actions **entirely client-side, never hitting the server**: `toggle_dark_mode` (persisted to `localStorage` under key `local_dark_mode`), `open_drawer`/`close_drawer`/`open_end_drawer`/ `close_end_drawer` (purely local UI state, intentionally _not_ persisted — drawers always start closed on reload).
-   Handles browser back/forward via `popstate`, keeping the URL bar in sync with the current content screen via `pushState`.

### Pending-Action Locks (`local_flare_pending_<action>`)

This is the SDK's built-in double-tap/race-condition guard, entirely automatic — you never wire it up manually. When the client parses a screen's layout JSON on init, it scans the whole tree for every distinct `flare_action` name referenced (`_extractFlareActions`), and registers a boolean DivKit variable `local_flare_pending_<action>` for each one, set to `false`.

The instant any `flare://action` fires:

1.  The client checks whether that exact action is already in flight _on that mount_. If so, the tap is silently ignored (no duplicate server round trip).
2.  Otherwise, it immediately sets `local_flare_pending_<action> = true` (before the network call even starts).
3.  The event is pushed through the mount's own channel.
4.  On the server's ACK (`ok`/`error`/`timeout` push reply), the client sets it back to `false`.

Your layout JSON can use this out of the box to disable/dim a button or swap its label while its own request is in flight:

```json
"alpha": "@{local_flare_pending_submit ? 0.5 : 1.0}",
"text":  "@{local_flare_pending_submit ? 'Saving...' : 'Save'}"

```

This is scoped **per mount** — a tap in flight on the bottom bar's own channel never freezes a button on the content screen's channel, and vice versa, because each Mount tracks its own `pendingActions` set independently.

### Building it

```bash
cd flare-web-client
npm install
npm run build       # bundles src/js, copies index.html/app.css/static/ into dist/

```

Output lands in `dist/`, served as static assets by your Phoenix `Endpoint`'s `Plug.Static` (`from: Path.expand("../../../../flare-web-client/dist", __DIR__)` — see [Getting a New Project Up and Running](https://claude.ai/chat/594413f3-2e86-417b-b7bd-00ffdf283354#step-3--build-the-web-client) for why this relative path matters).

## The Android Client

Lives in `flare-android-client/` — a standard Gradle Android project mirroring the web client's architecture almost exactly:

-   **`PhoenixChannelClient.java`** — a hand-rolled Phoenix Channels protocol v2 client on top of OkHttp WebSockets (join/leave/push, exponential-backoff reconnect, heartbeat, presence).
-   **`FlareClientActivity.java`** — the runtime Activity: owns the socket lifecycle, DivKit `Div2View` rendering, the same Mount abstraction (content mount + persistent scaffold-region mounts, each with its own channel and pending-action set), Android back-stack navigation (mirroring the web client's browser history), and command dispatch.
-   **`FlareDivActionHandler.java`** — intercepts `flare://action` taps, resolves URL query params (primary path, matches the web client) and legacy payload-based `@{...}` expressions (fallback path, via reflection against DivKit's internal variable store — see the extensive in-file comments for the 3-tier fallback strategy and why it exists).
-   **`NativeFeatureBridge.java`** — the extension point for native features (camera, QR scan, etc.) triggered from server-driven JSON via a `local_flare_native_action` payload key.

Building it is a standard Gradle Android project — open `flare-android-client/` in Android Studio, or build from the command line with `./gradlew assembleDebug`. It expects the same `ws://<host>/socket` endpoint and the same `/auth/*` HTTP endpoints your Phoenix app already exposes for the web client — point `MainActivity`'s server URL field at your running server (the emulator default, `10.0.2.2`, refers to your host machine's `localhost`).

This document intentionally does not go deeper into Android internals — if you're building an Android app on Flare, read `FlareClientActivity.java`'s own extensive inline documentation directly; it explains the multi-mount architecture, threading model, and command handling in detail comparable to this document's web-client section.

## The Project Generator Script

`create_flare_project.py` is a standalone Python 3 script with no external dependencies (standard library only: `os`, `re`, `shutil`, `sys`, `pathlib`). It is designed to be run from inside the folder that contains `flare/`, `flare-android-client/`, `flare-web-client/`, `flare_app_template/`, `.gitignore`, and `README.md` — it resolves everything relative to its own file location (`Path(__file__).resolve().parent`), so it doesn't matter what your current working directory is when you invoke it.

### What it asks for

1.  **Project name** — sanitized into a valid Elixir app name via `snake_case()` (lowercased, spaces/hyphens → underscores, invalid characters stripped, leading-digit names get an `app_` prefix). The PascalCase module prefix is derived automatically (`pascal_case("flare_app_template") == "FlareAppTemplate"`).
2.  **Destination folder** — expanded (`~` supported) and created if it doesn't exist. If `<destination>/<project_name>/` already exists, you're asked to confirm an overwrite (which deletes and recreates it).

### What it does

1.  Creates `<destination>/<project_name>/`.
2.  **Copies verbatim** (`shutil.copytree`/`copy2`, zero content modification) — `flare/`, `flare-android-client/`, `flare-web-client/`, `.gitignore`, `README.md` — skipping only known build-artifact directories (`_build`, `deps`, `node_modules`, `.git`, `.elixir_ls`, `cover`, `.dart_tool`, `.idea`, `.vscode`, `__pycache__`) and stale dev-database files (`.db`, `.db-shm`, `.db-wal`, `.DS_Store`) — these get regenerated by `mix deps.get`/`npm install`/`mix ecto.create` anyway, so shipping them would just be dead weight.
3.  **Generates your app** by walking `flare_app_template/` and, for every file and directory name containing `flare_app_template`, renaming it to your project's snake_case name; for every text file's _contents_, replacing `FlareAppTemplate` → your PascalCase module prefix and `flare_app_template` → your snake_case app name. Binary files (images, `.ico`, etc.) are copied byte-for-byte with no text processing attempted (detected via a UTF-8 decode probe on the first 2KB — `is_probably_text_file()`).

### Why the folder layout is exactly what it is

The generated structure deliberately mirrors this framework repo's own layout:

```
<project_name>/
├── flare/                     ← sibling of your app, referenced via
│                                 {:flare, path: "../flare"} in mix.exs
├── flare-android-client/      ← sibling, unrelated to mix.exs
├── flare-web-client/          ← sibling, referenced via relative
│                                 Path.expand("../../../../flare-web-client/dist", ...)
│                                 in both endpoint.ex and page_controller.ex
├── .gitignore
├── README.md
└── <project_name>/            ← your Phoenix app, `cd` here to run mix commands

```

**This exact sibling relationship is load-bearing** — both the Elixir `path:` dependency and the two hardcoded `Path.expand` calls in your generated app assume this depth. If you need to move folders around after generation, update `mix.exs`'s `{:flare, path: "../flare"}` and the two `Path.expand` calls in `lib/<app>/http/endpoint.ex` and `lib/<app>/http/controllers/page_controller.ex` accordingly.

### Clients ship unedited on purpose

`flare-android-client/` and `flare-web-client/` are copied as-is, completely untouched, specifically so **you** make the package-name, bundle-ID, app-name, and WebSocket-URL edits yourself, deliberately and explicitly, rather than the generator guessing at them. This is a conscious design choice: those values (Android `applicationId`, iOS bundle identifier if/when that client exists, app display name, socket URL for prod vs. dev) are exactly the kind of thing that's dangerous to auto-rewrite with regex — better for a human to make those changes once, correctly.

## Troubleshooting / FAQ

**"Missing config: config :flare, router: MyApp.FlareRouter"** — you haven't set `config :flare, router: ...` in your `config.exs`, or your router module name is wrong.

**Channel join fails with `"authentication_required"` for every user, even ones who logged in successfully** — your `UserSocket.connect/3` isn't assigning `:user_id` onto the socket. Double-check it calls `assign(socket, :user_id, user_id)` on the success path.

**"Router has roles: restrictions but no role_resolver configured"** — you added `roles: [...]` to a screen in the router without setting `config :flare, role_resolver: {Module, :function, 1}`. Flare fails closed here on purpose (denies access rather than silently opening it up), so add the config line.

**A layout change isn't showing up after I edited the JSON file** — the screen is `use_cache true` (the default) and you haven't restarted the server or called `Flare.update_layout/2`. Either set `use_cache false` temporarily during active development of that screen, restart `mix phx.server`, or call `Flare.Layout.invalidate(screen_name)` / `Flare.update_layout(user_id, screen_name)` from an IEx shell.

**`local_dark_mode` (or another `local_` variable) keeps resetting to its JSON default every time I navigate** — check that the client is actually implementing the "don't clobber an existing `local_` variable's value with the new screen's default" guard on `"init"` (both shipped clients do this out of the box — see the relevant section under [The Web Client](https://claude.ai/chat/594413f3-2e86-417b-b7bd-00ffdf283354#the-web-client)). If you're writing a custom client, this is the one behavior you must replicate exactly, or dark mode/drawer state will visibly flicker/reset on every navigation.

**I set a `flare_` variable from the server but it never appears on the client** — confirm the variable is declared in that screen's `state/<screen>.json` (the client needs a type definition to bind an expression to). A value assigned server-side without a matching state-JSON declaration will still be included in diffs/patches, but if it's the very first time the client ever sees that variable name (not present in `state/*.json`), the web/Android clients infer a type from the raw JSON value (boolean/integer/number/string) — arrays and objects specifically are **skipped** if there's no declared type, since inferring a DivKit array/dict variable type from a raw value isn't safely possible. Always declare array/dict-typed `flare_` variables in `state/*.json` explicitly.

**Two channels for the same screen name are both open for one user and state seems to leak between them** — this shouldn't happen under normal navigation (the client only ever has one content mount, plus fixed persistent scaffold mounts), but if you're writing custom client code that opens multiple simultaneous channels to the _same_ screen name for one user, be aware `Flare.Channel.leaveOpenTopic/1` (server) actively leaves any other JOINED/JOINING channel on the same topic before a rejoin — this is a duplicate-subscription guard, not a feature to build on top of.

**Guests can't access a screen I want them to be able to use** — check `authorize/2` on that screen or its module for a `def authorize("guest_" <> _, _params), do: {:error, ...}` clause (the shipped template blocks guests from `PlaceSetup`/`WindowSetup`-style "create something persistent" screens, since guest identities have no durable row in the `users` table and can't be reliably attributed to later). Remove or adjust that clause if guests should be allowed.

**How do I add a brand-new one-time announcement without a migration?** — if you're using the `Overlay` scaffold pattern, just append a new `%{key: "some_new_key", message: "..."}` entry to the module's `@announcements` list. The `OverlaySeenFlag` schema already supports arbitrary `flag_key` strings with no schema change required per announcement.








# 🔥 Flare

**Server-Driven UI for Elixir + Phoenix & DivKit.**

Build native Android and Web apps from a single Elixir codebase. The server owns all UI and business logic. Clients simply render the JSON layouts the server sends, fire events when the user taps, and update their UI variables when patches arrive from the server. Nothing more.



---



## How it works

Every screen in your app is a Phoenix Channel topic (e.g., `flare:welcome`). When a client joins, the server sends a full screen layout as DivKit JSON, plus the current state. When the user taps a button, the client pushes an event. The server runs your Elixir handler, computes what changed, and pushes back only the diff (a patch). The client applies it.

No page reloads, no REST APIs, no client-side routing logic.

```text
Client joins "flare:welcome"
  → Server sends INIT  { layout: <divkit json>, state: { flare_count: 3 } }
  → Client renders the screen

User taps "+"
  → Client pushes  { type: "increment", payload: {} }
  → Server runs handle_event, assigns flare_count: 4
  → Server computes DIFF: only flare_count changed
  → Server sends PATCH { state: { flare_count: 4 } }
  → Client updates the variable, DivKit instantly re-renders the number
```

---

## Variable System

Flare uses a three-tier variable system. Understanding this is the key to understanding Flare.

### 1. `flare_` — server-owned, persisted across screens
Variables prefixed with `flare_` are the only variables the server cares about. They are cached automatically in RAM and restored automatically when a user navigates to a new screen.

```elixir
# In your Elixir event handlers:
socket |> assign(:flare_count, 5)
```

### 2. `local_` — client-owned, never sent to server
Variables prefixed with `local_` exist *only* on the client. The server never sees them, stores them, or diffs them. They are lost when the user navigates to a new screen.

Use them for UI-only state: text input values before submission, tab selections, or toggle states.

```json
{ "type": "input", "text_variable": "local_first_name" }
```
```json
{
  "payload": {
    "flare_action": "save_profile",
    "first_name": "@{local_first_name}"
  }
}
```
*Note: The client SDK automatically resolves `@{local_first_name}` to the actual typed text before sending the payload to the server.*

### 3. `local_flare_pending_<action>` — SDK reserved, automatic
These are created automatically by the Flare client SDK for every action found in your layout.

When a user taps a button that fires `flare_action: "increment"`, the SDK immediately sets `local_flare_pending_increment = true`. When the server replies, it sets it back to `false`.

Use them in your layout to give instant visual feedback without writing any JS or Android code.
